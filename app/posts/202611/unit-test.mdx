AI にコードを書かせるようになってテストがより大事になってきたと思います  
品質の担保はもちろん、AI が作ったコードがどこかを壊していないか検知できるのもテストです

ただ、テストコードも AI がどかどか大量に作ってくれるようになり、
ちゃんとテストできているか心配だしテストケース量が多すぎるとチェックも大変です、、  

なので、テスト (特に単体テスト) について少し調べて学んだことをメモがてらまとめます

## 1. 単体テストには学派があるらしい

単体テストには「古典派」と「ロンドン派」という学派があります
単体テストに学派があることを知りませんでした、、

違いはざっくり以下です

- ロンドン派
  - テスト対象の依存をすべてモックにして、呼び出し (相互作用) を検証する
  - `単体`はクラスなどのコードの単位
- 古典派
  - DB や外部 API など扱いにくい依存以外は本物を使って、状態や結果を検証する
  - `単体`は振る舞いの単位

学派の存在は知りませんでしたが個人的には古典派で書いていると思います  
振る舞いをテストするほうが不用意にテストパターンが増えないし、メンテもしやすいと思います
( 以前、いわゆるロンドン派でテストが書かれていた機能があったのですが、モックを直すのが大変だった思い出があります、、 )

## 2. そもそも誤りを書けないように実装する

テストパターンが増やされないようにそもそも誤りを書けないように実装するという考え方もあります  
例えば lint などを使えば、テストを書かなくても機械的に誤りを弾いてくれます

さらに以下をやると、書くべきテストのパターンを減らせます

- 引数をユーザー定義型 (値オブジェクト) にする
- 判別可能な union (代数的データ型) を使う

### 2.1. 引数をユーザー定義型 (値オブジェクト) にする

例えば引数で価格を `number` で受け取ると、負の数や小数などどんな数値でも渡せてしまいます  
なので、価格を受け取る関数ではそれぞれ異常な金額をチェックする必要があります

```ts
// 税額を計算する
const calcTax = (price: number) => {
  if (!Number.isInteger(price) || price < 0) throw new Error("不正な金額です")
  return Math.floor(price * 0.1)
}

// 送料無料か判定する
const isFreeShipping = (price: number) => {
  if (!Number.isInteger(price) || price < 0) throw new Error("不正な金額です")
  return price >= 5000
}
```

このときに書くテストは以下

- `calcTax`: 正常な金額、負の数、小数、`NaN`
- `isFreeShipping`: 5000 未満、5000 以上、負の数、小数、`NaN`

異常な金額のテストが関数ごとに発生してしまいます  
価格を受け取る関数が増えるほど、同じようなテストも増えていきます

そこで、条件を満たした値しか作れない型にして、それを引数で受け取るようにします

```ts
class Price {
  private constructor(readonly value: number) {}

  static of(n: number): Price | null {
    if (!Number.isInteger(n) || n < 0) return null
    return new Price(n)
  }
}

const calcTax = (price: Price) => Math.floor(price.value * 0.1)

const isFreeShipping = (price: Price) => price.value >= 5000
```

こうすると各関数に異常な金額が渡ってくることはないのでテストは以下で済みます

- `Price.of`: 正常な金額、負の数、小数、`NaN`
- `calcTax`: 正常な金額
- `isFreeShipping`: 5000 未満、5000 以上

異常な金額のチェックは `Price` で担保しているので、各関数からはその分のテストを削れます  
関数ごとに余計なテストパターンを減らせて、それぞれの関数が満たすべき振る舞いのテストに集中できます

### 2.2. 判別可能な union (代数的データ型)

例えば状態を boolean の組み合わせで持つと、ありえない組み合わせも作れてしまいます

```ts
// 2^3 = 8 通り作れるけど、支払い前に発送済みのようなありえない状態も含まれる
type Order = {
  isPaid: boolean
  isShipped: boolean
  isCanceled: boolean
}

// キャンセルできるか判定する
const canCancel = (order: Order) => !order.isShipped && !order.isCanceled
```

`canCancel` は引数で 8 通りの組み合わせを受け取れてしまいます  
なので、「支払い前に発送済み」のようなありえない組み合わせが来たときどうなるかもテストしたくなります
( もちろん AI がその分だけテストを作ってくる可能性があります )

判別可能な union にすると、ありえる状態だけを表現できます

```ts
type Order =
  | { status: "unpaid" }
  | { status: "paid"; paidAt: Date }
  | { status: "shipped"; paidAt: Date; shippedAt: Date }
  | { status: "canceled"; canceledAt: Date }

const canCancel = (order: Order) => {
  switch (order.status) {
    case "unpaid":
    case "paid":
      return true
    case "shipped":
    case "canceled":
      return false
  }
}
```

引数で受け取れるパターンが 4 通りに制限されるので、`canCancel` のテストも 4 パターンで済みます  
ありえない組み合わせのテストはそもそも書けなくなります

※ さらに typescript であれば eslint の `switch-exhaustiveness-check` を使えば、`switch` で状態の考慮漏れがあると lint で気づけます

## 3. ミューテーションテストでテストをテストする

あるテストがちゃんと対象の振る舞いを確認できているかを測る方法として`ミューテーションテスト`というものがあります  
ざっくりいうと、実装コードをわざと書き換えて (壊して) テストが落ちるか確認する手法です
(書き換えたコードを `ミュータント` といいます)

各テストパターンを以下に振り分けます

- Killed
  -  書き換えたらテストが落ちた
  - ⇒ テストが壊れたことを検知できている
- Survived
  - 書き換えてもテストが通ってしまった
  - ⇒ テストが壊れたことを見逃している

例えば以下のような関数があったとして、

```ts
const isBiggerThanThree = (n: number) => n > 3
```

`0` を渡すテストだけだと、`>` を `>=` に書き換えても結果は `false` のままなのでテストは通ってしまいます  
つまり、境界値のテストが足りていないことがわかります

カバレッジのみだとそのコードを通ったかしかわからないので、テストの中身がちゃんと検証できているかを見るのに良さそうです

また、ミューテーションテストを行うことで意味を成していない余計なテストを削り、逆に足りてないテストを追加することができそうです

## 4．まとめ

- 単体テストには古典派とロンドン派がある
- そもそも型や lint で誤りを書けないようにすると、書くべきテストを減らせる
- ミューテーションテストでテストコード自体の質を測れる

AI にテストを書かせるときも、学派や今回の書き方はスキルや rules で指定しておきたいなと思います  
ミューテーションテストはまだやったことがないので、できそうなときがあったらぜひ試してみたいです
